# Commands v3 method lookup

A task-based guide to the Java command API in WPILib 2027 Alpha 8, with explanations and examples. [Look up a v2 method](reference.html).

## Build a command

- **`Command.noRequirements`** Starts a builder with no mechanism requirements. Pass a lambda that accepts one `Coroutine` and returns no value. Java calls that type `Consumer<Coroutine>`. Use it for console output, bookkeeping, or a routine whose child commands take their own requirements. Finish with `.named(...)`. [Trace a console command](coroutines.html#trace-a-pause-and-resume).
- **`Command.requiring` / `NeedsExecutionBuilderStage.requiring`** Declare the mechanisms the command reserves for its entire run. Start with a mechanism and optional additional mechanisms, or pass a collection. Add more requirements on the builder before supplying the body. [Reserve drive before reading its pose](examples-command-groups.html#build-a-command-from-the-robot-s-current-state).
- **`NeedsExecutionBuilderStage.executing`** Supplies the body lambda after requirements have been declared. WPILib passes the `Coroutine` into that lambda when the scheduler starts the command. Put state reads in the lambda to read them during each run. The resulting builder accepts lifecycle options and a name. [Build a drive command at run time](examples-command-groups.html#build-a-command-from-the-robot-s-current-state).
- **`Mechanism.run`** Starts a builder that automatically requires the receiver. Put it on the mechanism class when the body sets outputs, waits for a condition, or performs several steps. A body that returns without pausing runs once. [Translate a sensor-driven intake](intake.html#translate-the-intent).
- **`Mechanism.runRepeatedly`** Starts a builder that requires the receiver and calls a short action every scheduler cycle. Pass a zero-argument lambda or a method reference. WPILib supplies the loop and yields between calls. Use it for joystick updates or another repeated action and pair it with an exit action if outputs need cleanup. [Keep drive stopped during a timed pause](examples-command-groups.html#keep-the-drivetrain-stopped-during-an-autonomous-pause).
- **`NeedsNameBuilderStage.named` / `ParallelGroupBuilder.named` / `SequentialGroupBuilder.named`** Finalize a builder and return a command you can bind, schedule, or compose. Pick a name that makes sense in a scheduler log, and set builder options before finalizing. [See the builder-versus-command compile error](changes.html#finish-building-and-name-the-command).
- **`ParallelGroupBuilder.withAutomaticName` / `SequentialGroupBuilder.withAutomaticName`** Finalize a group with a generated name based on its composition. Use an explicit name when a label such as “Prepare to score” would be easier to recognize. For example, `Command.sequence(deploy, collect).withAutomaticName()`. [Compare sequence and coroutine code](ownership.html#move-the-drivetrain-then-position-the-elevator).
- **`NeedsNameBuilderStage.withPriority`** Sets the command’s priority before naming. A lower-priority incoming command cannot take a shared mechanism from an ordinary running command. Use `Command.LOWEST_PRIORITY` for a default that should readily yield to other commands. [See the joystick default](changes.html#set-priorities-and-defaults).
- **`NeedsNameBuilderStage.whenExited` / `Command.onExit`** Register a zero-argument cleanup lambda or method reference with the builder, or override the exit hook when implementing `Command` directly. It runs after a started command finishes or is canceled. One typical use is `.whenExited(this::stop)`, which still stops the roller when cancellation skips the rest of the body. [Trace both exit paths](coroutines.html#trace-a-pause-and-resume).
- **`NeedsNameBuilderStage.whenCanceled` / `Command.onCancel`** Register or implement an action for cancellation of a started command. Use it for a cancellation report and use the exit hook for cleanup needed on every exit. For example, combine `.whenCanceled(this::reportInterrupted)` and `.whenExited(this::stop)` before naming. [Compare cancellation and cleanup](changes.html#handle-completion-timeout-and-cancellation).
- **`Command.run`** Lifecycle method the scheduler invokes with a coroutine. Implement it if you write a `Command` class directly. To run a command from robot code, schedule it or use it as a child. [See how a builder supplies the body](coroutines.html#trace-a-pause-and-resume).
- **`Command.name` / `Command.requirements` / `Command.priority`** Inspect a finished command’s name, required mechanisms, and priority. They help explain what you see in scheduler logs. For example, `command.requirements()` can tell you which mechanisms a sequence reserves between stages. [Trace a sequence’s requirements](ownership.html#move-the-drivetrain-then-position-the-elevator).
- **`Command.requires` / `Command.conflictsWith` / `Command.isLowerPriorityThan`** Test whether a command requires one mechanism, whether two commands share requirements, or whether this command has strictly lower priority. For instance, `incoming.conflictsWith(running)` identifies overlapping requirements. To ask about other scheduler rules too, use [`Scheduler.isSchedulable`](#schedule-and-inspect-commands). [See a priority conflict](changes.html#set-priorities-and-defaults).
- **`StagedCommandBuilder.noRequirements` / `StagedCommandBuilder.requiring`** These factories expose the same staged builder used by `Command.noRequirements` and `Command.requiring`. For ordinary robot code, start with the `Command` factories. [See the staged construction of a drive command](examples-command-groups.html#build-a-command-from-the-robot-s-current-state).

## Pause, wait, and end

- **`Coroutine.yield`** Pauses the current body so the scheduler can run other work. When the scheduler resumes it, the call returns `true` and execution continues on the next line with local variables intact. In a control loop that spans scheduler cycles, every repeating path should give the scheduler a turn. [Trace the call and return](coroutines.html#trace-a-pause-and-resume) · [Keep the scheduler responsive](coroutines.html#put-yield-where-the-loop-repeats).
- **`Coroutine.park`** Pauses indefinitely. Use it after applying a persistent output when another event, such as a button release, will cancel the command. Put cleanup in `whenExited` because the code after `park()` will never run. [Hold a roller on until release](examples-operator-controls.html#run-a-roller-while-a-button-is-held).
- **`Coroutine.wait`** Pauses the current body for a typed duration, then continues the same command. For example, `coroutine.wait(Seconds.of(1))` inserts a delay while the command keeps its own requirements. A zero or negative duration returns immediately. [Compare pause operations](coroutines.html#choose-how-to-pause).
- **`Coroutine.waitUntil` / `WaitResult.timedOut`** Wait for a condition in the current body, optionally with a maximum duration. Pass a zero-argument lambda or method reference that returns `boolean`, such as `this::hasGamePiece`. It supplies a fresh result each time WPILib checks the condition. The timed overload lets the body branch on `result.timedOut()`, which is true for `TIMED_OUT` and false for `CONDITION_MET`. [Report an intake timeout and still clean up](examples-sensor-waits.html#collect-a-game-piece-with-a-time-limit).
- **`Command.waitFor` / `Command.waitUntil`** Build standalone wait commands with no requirements. Use these when a group or another API takes a `Command` object. For a sensor gate, `Command.waitUntil(intake::hasGamePiece).named("Wait for piece")` builds the command you can put in the group. [Use a timer as a race participant](ownership.html#race-a-sensor-against-a-timeout).
- **`Command.withTimeout` / `Command.until`** Wrap a finished command with a time limit or an early-stop predicate. If the wrapper’s limit wins, it cancels the original command. `withTimeout(Seconds.of(2))` returns a finished command. `until(condition)` returns a parallel group builder that needs a name. [Compare decorator return types](changes.html#finish-building-and-name-the-command).
- **`NeedsNameBuilderStage.until` / `SequentialGroupBuilder.until` / `ParallelGroupBuilder.until`** Set an early-stop condition on a builder, before naming it. On group builders the latest `until` call replaces the previous condition. For example, `Command.sequence(approach, align).until(this::abortRequested).named("Approach and align")`. [Choose between a group and a coroutine](ownership.html#choose-a-group-or-a-coroutine).
- **`Coroutine.requestCancellation`** Cancels this coroutine and its children. Use an ordinary `return` to finish successfully. This method is mainly useful to a helper that has the coroutine but cannot return from its caller’s command body. For example, `if (abortRequested()) coroutine.requestCancellation();`. [Compare completion and cancellation](intake.html#follow-the-command).

## Compose command groups

- **`Command.sequence` / `Command.andThen` / `SequentialGroupBuilder.andThen`** Build a fixed sequence. The static factory takes commands in order, the instance method starts a sequence with an existing command, and the builder method appends more steps. The group reserves the combined requirements across the whole sequence. [Compare group and child ownership](ownership.html#move-the-drivetrain-then-position-the-elevator).
- **`Command.parallel` / `Command.alongWith` / `ParallelGroupBuilder.alongWith`** Start several commands together and wait for all of them. The builder’s `alongWith` adds one more child that must finish. Give concurrent children disjoint requirements. [Use a parallel preparation stage](ownership.html#use-a-group-inside-a-coroutine).
- **`Command.race` / `Command.raceWith`** Build a parallel group where the first child to finish ends the group and cancels the rest. `collect.raceWith(timer).named("Timed collection")` is the instance form of `Command.race(collect, timer)`. [Race intake against a timer](ownership.html#race-a-sensor-against-a-timeout).
- **`ParallelGroupBuilder.requiring` / `ParallelGroupBuilder.optional`** Choose which child commands must finish. Optional children start alongside the required ones and are canceled when all required children finish. With only optional children, the group races them. Both kinds contribute mechanism requirements to the group. [Use a timer as the deadline while stopping drive](examples-command-groups.html#keep-the-drivetrain-stopped-during-an-autonomous-pause).
- **`ConflictDetector.findAllConflicts` / `ConflictDetector.throwIfConflicts`** Check a collection of proposed parallel children for overlapping mechanism requirements. Use `findAllConflicts` to show all overlaps in diagnostics or `throwIfConflicts` to reject an invalid collection. For example, check `ConflictDetector.findAllConflicts(children).isEmpty()` before building a group assembled from configuration.
- **`Conflict.a` / `Conflict.b` / `Conflict.sharedRequirements` / `Conflict.description`** Read the two commands, their shared mechanisms, or a diagnostic description. For example, `ConflictDetector.findAllConflicts(children).forEach(c -> log(c.description()))` reports each pair that would compete. [See a parallel group with independent mechanisms](ownership.html#prepare-two-independent-mechanisms-together).

## Run children from a coroutine

- **`Coroutine.await`** Start a child and pause the parent until it finishes. Use separate `await` calls when you want to read state or make a decision between actions. A parent with no requirements lets each child acquire and release its own mechanisms. [Drive, then move the elevator](ownership.html#move-the-drivetrain-then-position-the-elevator).
- **`Coroutine.awaitAll` / `Coroutine.awaitAny`** Start or wait on several children passed as arguments or in a collection. `awaitAll` waits for all of them. `awaitAny` resumes the parent after one finishes and cancels the others. An `awaitAny` result reports whether the children could start, so use a sensor reading or an explicit timeout result when the parent needs to decide what happened. [Wait for both actions](ownership.html#prepare-two-independent-mechanisms-together) · [Race a sensor against time](ownership.html#race-a-sensor-against-a-timeout).
- **`Coroutine.fork`** Start children passed as arguments or in a collection and continue the parent without waiting for them to finish. Any child still running when the parent exits is canceled. [Keep lights running while drive completes](ownership.html#start-a-child-and-keep-going-with-fork).
- **`Coroutine.setCancelOnForkFailure` / `Coroutine.isCancelOnForkFailure`** Change or read the parent’s policy when a child cannot be started. The default cancels the parent. To choose your own fallback, call `coroutine.setCancelOnForkFailure(false)` before the attempt and handle the returned result. [See why a blocked child can end a routine](examples-command-groups.html#give-a-child-its-mechanism-only-while-it-runs).
- **`ForkResult.successful` / `ForkResult.failed` / `ForkResult.partialSuccess`** Check whether all requested children started, at least one failed to start, or the attempt had both successes and failures. With automatic cancellation disabled, a fallback can start with `if (coroutine.await(align).failed()) return;`. [See the fork and await comparison](ownership.html#start-a-child-and-keep-going-with-fork).
- **`ForkResult.awaitCompletion`** Wait for the children that this result successfully started and that are still running. Use `var result = coroutine.fork(lights); ...; result.awaitCompletion();` when you have other work to do first and want to join that exact run. [See a parent continue after forking](ownership.html#start-a-child-and-keep-going-with-fork).
- **`ForkResult.getFailedCommands` / `ForkResult.getForkedCommands`** Read the scheduling results for failures and successes. Use them for diagnostics when a multi-child start does not go as expected. For example, `result.getFailedCommands().forEach(f -> log(f.command().name()))`. [See scheduling result details](#schedule-and-inspect-commands).
- **`Coroutine.scheduler`** Get the scheduler that owns this coroutine when you need an advanced operation. Commands manually scheduled through it inside the body still belong to the parent’s lifetime. For example, call `coroutine.scheduler().cancel(child)` to stop one child early. [Trace a forked child’s lifetime](ownership.html#start-a-child-and-keep-going-with-fork).

## Configure mechanisms and defaults

- **`Mechanism.setDefaultCommand` / `Scheduler.setDefaultCommand`** Set the command the scheduler uses when a mechanism is free. The default must require exactly that mechanism. Use the mechanism method in ordinary setup or specify the mechanism explicitly on the scheduler. The scope where you install it determines how long the setting lasts. [Install joystick drive](changes.html#set-priorities-and-defaults) · [See how default scopes work](changes.html#tie-work-to-the-right-lifetime).
- **`Mechanism.getDefaultCommand` / `Scheduler.getDefaultCommandFor`** Read the current default setting for a mechanism. This helps diagnose which default is installed, even while another command controls the mechanism. For example, `drive.getDefaultCommand().name()` can identify the default in a diagnostic. [Compare the default with a competing command](changes.html#set-priorities-and-defaults).
- **`Mechanism.idle` / `Mechanism.idleFor`** Create a command requiring the mechanism without issuing output. `idle()` stays active until interrupted or canceled and uses the lowest priority. `idleFor(Seconds.of(1))` ends after the duration. If you need drive held at zero, explicitly command zero output. [Keep drive stopped during a pause](examples-command-groups.html#keep-the-drivetrain-stopped-during-an-autonomous-pause).
- **`Mechanism.getRegisteredScheduler` / `Mechanism.getName`** Inspect the scheduler used by the mechanism’s default and running-command helpers and the name used for the mechanism. The base implementations use the default scheduler and a name derived from the class. In a test with a separate scheduler, the mechanism can override `getRegisteredScheduler()` to return it. [See an independent scheduler setup](#schedule-and-inspect-commands).
- **`Mechanism.getRunningCommands` / `Scheduler.getRunningCommandsFor`** Inspect running commands attached to a mechanism, in schedule order. This can include both an owning parent and a child sharing the requirement. For example, `drive.getRunningCommands()` helps track who can use drive in each stage. [Trace requirements through a routine](ownership.html#move-the-drivetrain-then-position-the-elevator).
- **`Mechanism.controllableDuringDisabled`** Declares whether the scheduler may run commands requiring this mechanism while the robot is disabled. The default is false. For a mechanism that genuinely supports disabled operation, the override supplies that policy. [Review disabled behavior during a port](changes.html#move-periodic-work-and-check-disabled-behavior).

## Bind and combine triggers

- **`Trigger`** Create a trigger from a `BooleanSupplier`, optionally with an explicit scheduler and event loop. Use a method reference to read a button or sensor each time the loop polls. A constructor without a scheduler uses the default scheduler. [Bind a debounced sensor or a button](examples-advanced.html#bind-buttons-and-sensors).
- **`Trigger.onTrue` / `Trigger.onFalse`** Schedule a command on a transition to true or false. Use for a one-shot action on press or release. In Alpha 8, the first observed value can also fire the corresponding binding, so a release action must make sense before the first press. [Bind a button press and release](examples-advanced.html#bind-buttons-and-sensors).
- **`Trigger.ifTrue`** Attempts to schedule on each event-loop poll while the condition is true. An already-running command keeps running. When the condition becomes false, this binding stops making schedule requests and leaves the running command alone. For example, `pieceReady.ifTrue(processPiece)` lets an in-progress command finish after the signal drops. [Compare the hold behavior](examples-operator-controls.html#run-a-roller-while-a-button-is-held).
- **`Trigger.whileTrue` / `Trigger.whileFalse`** Start when the condition enters the requested level and cancel when it leaves. If the command finishes while the condition stays at that level, wait for another transition. Use for manual control that should stop when a button is released. [Run a roller while held](examples-operator-controls.html#run-a-roller-while-a-button-is-held).
- **`Trigger.retryWhileTrue` / `Trigger.retryWhileFalse`** Use the same start and cancel conditions as the corresponding `while` binding, with retries as long as the active level persists. Choose this if a short command should run again during the same hold. For example, `cycleButton.retryWhileTrue(intakePulse)` retries a completed pulse. [Compare the two hold bindings](examples-operator-controls.html#choose-a-binding-for-a-held-button).
- **`Trigger.toggleOnTrue` / `Trigger.toggleOnFalse`** Alternate between starting and canceling the command on successive transitions of the selected kind. This is useful for a latched mode such as a practice display. For example, `displayButton.toggleOnTrue(showStatus)` uses successive presses. [WPILib docs · Toggle Bindings](https://docs.wpilib.org/en/latest/docs/software/commandbased/commands-v3/triggers.html#toggle-bindings).
- **`Trigger.and` / `Trigger.or` / `Trigger.negate`** Build triggers from both conditions, either condition, or the inverse condition. Bind the returned trigger. For example, `runButton.and(this::clearToRun).whileTrue(collect)` stops the hold if either condition becomes false. [Combine a button with a condition](examples-advanced.html#bind-buttons-and-sensors).
- **`Trigger.debounce`** Return a trigger that filters short changes. Pass a typed duration to debounce rising edges, or choose rising, falling, or both edges with a `DebounceType`. Use this for a sensor whose signal flickers. [Debounce a piece sensor](examples-advanced.html#bind-buttons-and-sensors).
- **`Trigger.risingEdge` / `Trigger.fallingEdge`** Turn a transition into a trigger active for one event-loop cycle. Use `risingEdge()` for a false-to-true pulse and `fallingEdge()` for true-to-false. For a plain one-shot binding, `onTrue` or `onFalse` already detects the edge. [WPILib docs · Modifying Trigger Behavior](https://docs.wpilib.org/en/latest/docs/software/commandbased/commands-v3/triggers.html#modifying-trigger-behavior).
- **`Trigger.multiPress`** Return a trigger that becomes active when the specified number of rising edges fits within the time window. For example, `button.multiPress(2, Seconds.of(0.4)).onTrue(mark)` responds to a double press. [WPILib docs · Multi-Press Bindings](https://docs.wpilib.org/en/latest/docs/software/commandbased/commands-v3/triggers.html#multi-press-bindings).
- **`Trigger.getAsBoolean`** Read the cached value from the most recent poll. It is false before the first poll and can lag a raw input read between polls. Use the original sensor method when you need to sample the underlying signal directly. [See trigger configuration](examples-advanced.html#bind-buttons-and-sensors).
- **`RobotModeTriggers.autonomous` / `RobotModeTriggers.teleop` / `RobotModeTriggers.disabled` / `RobotModeTriggers.utility`** Get a trigger for the selected robot mode. For example, `RobotModeTriggers.disabled().onTrue(reportStatus)` binds a status action to entering disabled. Commands still have to meet the scheduler’s requirements for running in that mode. [Review mode and binding scope](changes.html#tie-work-to-the-right-lifetime).

## Schedule and inspect commands

- **`Scheduler.getDefault` / `Scheduler.createIndependentScheduler`** Get the shared robot scheduler or make a separate instance for an isolated test. Put the test’s triggers, mechanisms, and callbacks on that same scheduler, and drive its loop explicitly. [Run an independent scheduler](examples-advanced.html#schedule-and-inspect-a-command).
- **`Scheduler.run` / `Scheduler.getDefaultEventLoop`** Process one scheduler cycle. This polls the default event loop and advances runnable commands, including continuing coroutines that are ready to resume. Use the event-loop accessor when setting up polling for custom trigger arrangements. [Step a scheduler through a command](examples-advanced.html#schedule-and-inspect-a-command).
- **`Scheduler.schedule` / `Scheduler.isSchedulable`** Submit a command to run, or check eligibility without submitting it. Both return a `ScheduleResult`. A check reflects the current state, so use the result of `schedule` to learn what actually happened. [Check a scheduling attempt](examples-advanced.html#schedule-and-inspect-a-command).
- **`Scheduler.cancel` / `Scheduler.cancelAll`** Cancel one queued or running command and its descendants, or cancel all queued and running commands. Defaults can be scheduled again on the next cycle. [Cancel a command while it is paused](examples-advanced.html#schedule-and-inspect-a-command).
- **`Scheduler.isScheduled` / `Scheduler.isRunning` / `Scheduler.isScheduledOrRunning`** Ask whether a command is queued, has started and is still active, or is in either state. A coroutine that yielded can still be running in this sense. Use the combined check to tell whether a submitted command is still active or pending. [Inspect the queued and running states](examples-advanced.html#schedule-and-inspect-a-command).
- **`Scheduler.getQueuedCommands` / `Scheduler.getRunningCommands`** Inspect collections of pending and running commands. For example, `scheduler.getRunningCommands().forEach(c -> log(c.name()))` can help explain active behavior. Alpha 8 marks the queue accessor for internal use. [Inspect a command in a scheduler loop](examples-advanced.html#schedule-and-inspect-a-command).
- **`Scheduler.currentCommand` / `Scheduler.getParentOf`** Find the command executing on the scheduler call stack, or find the parent of a running child. Both can return `null`. The parent accessor is marked for internal use. [See how parent and child runs relate](ownership.html#start-a-child-and-keep-going-with-fork).
- **`Scheduler.lastCommandRuntimeMs` / `Scheduler.totalRuntimeMs` / `Scheduler.lastRuntimeMs`** Measure execution time in milliseconds for one command’s last cycle, that active command’s current run, or the scheduler’s last cycle. Use these to find code that takes too long inside a scheduler cycle. The command metrics return `-1` if the command is not running. [Read cycle timings](examples-advanced.html#schedule-and-inspect-a-command).
- **`Scheduler.runId` / `Successful.runId`** Identify an individual run of a reusable command object. The scheduler’s lookup returns zero after the run is no longer queued or running. A successful scheduling result retains its assigned ID, even for a short run. A predictive check can report zero because no ID has been assigned yet. [Inspect the schedule result](examples-advanced.html#schedule-and-inspect-a-command).
- **`ScheduleResult.command` / `ScheduleResult.successful` / `Success.command` / `Success.runId` / `AlreadyRunning.command` / `AlreadyRunning.runId`** Inspect which command the result describes and whether scheduling succeeded. `AlreadyRunning` is a successful result for an existing run and supplies that run’s ID. For example, `if (result instanceof Scheduler.ScheduleResult.Successful ok) log(ok.runId());`. [Handle a schedule result](examples-advanced.html#schedule-and-inspect-a-command).
- **`Failure.successful` / `Successful.successful` / `LowerPriorityThanQueuedCommand.command` / `LowerPriorityThanQueuedCommand.queuedCommand` / `LowerPriorityThanRunningCommand.command` / `LowerPriorityThanRunningCommand.alreadyRunning` / `RequiresUnsafeMechanisms.command` / `RequiresUnsafeMechanisms.unsafeMechanisms`** Failures expose the requested command and, depending on the result type, the blocking command or the unavailable mechanisms. Use the result subtype to explain the failure in diagnostics. [See priority and disabled conflicts](changes.html#set-priorities-and-defaults).
- **`Scheduler.addPeriodic` / `Scheduler.sideload`** Register supporting work for the scheduler. `addPeriodic` runs a short callback each cycle. `sideload` accepts a coroutine body that can pause and finish under its own control. Use these for bookkeeping, simulation updates, or reporting that does not take control of mechanisms. [Add a periodic scheduler callback](examples-advanced.html#schedule-and-inspect-a-command).
- **`Scheduler.addEventListener` / `SchedulerEvent.timestampNanos`** Subscribe to scheduler events and read their timestamps. Keep the listener quick and use it for observation, such as noting when a command was interrupted. Scheduling or canceling commands inside the listener can disrupt scheduler processing. [Log an interruption](examples-advanced.html#schedule-and-inspect-a-command).
- **`Canceled.command` / `Completed.command` / `CompletedWithError.command` / `ForkFailure.command` / `Interrupted.command` / `Mounted.command` / `Scheduled.command` / `Yielded.command`** Get the command associated with a scheduler event. These records also implement `SchedulerEvent.timestampNanos()`. Match a specific record type to decide which events to log. [Log an interruption](examples-advanced.html#schedule-and-inspect-a-command).
- **`Interrupted.interrupter` / `CompletedWithError.error` / `ForkFailure.failures`** Inspect the other command, the thrown error, or the list of child scheduling failures that explains the event. For example, `event instanceof SchedulerEvent.Interrupted interrupted` gives access to `interrupted.interrupter()`. [Log an interruption](examples-advanced.html#schedule-and-inspect-a-command).

## Define a state machine

- **`StateMachine` / `StateMachine.addState` / `StateMachine.setInitialState`** Create a named command whose states each run a command. Add the states, define transitions, and choose the initial state before scheduling the machine. Use a state machine when named states and transitions express reactive behavior clearly. [Build a collection state machine](examples-advanced.html#switch-between-collection-and-ready).
- **`State.switchTo` / `State.exitStateMachine`** Start defining where a transition from this state goes. `switchTo` takes a fixed state or a supplier evaluated when the transition fires. `exitStateMachine` makes the target the end of the whole machine. Finish either with a transition condition. [Switch into a ready state](examples-advanced.html#switch-between-collection-and-ready).
- **`StateMachine.switchFromAny` / `TransitionNeedsTargetStage.to` / `TransitionNeedsTargetStage.toExitStateMachine`** Set up one transition for several source states. Choose a fixed or computed target with `to`, or end the machine with `toExitStateMachine`. With no source arguments, the transition applies to all states already added and seals the state list. [Allow operator cancellation from every state](examples-advanced.html#switch-between-collection-and-ready).
- **`TransitionNeedsConditionStage.when` / `TransitionNeedsConditionStage.whenComplete` / `TransitionNeedsConditionStage.whenCompleteAnd`** Finish a transition rule. Use `when` for a rising condition observed during the active state, `whenComplete` for completion, and `whenCompleteAnd` to test a condition at completion. Conditional completion transitions are tried in declaration order before the unconditional completion fallback. [Branch on a sensor after a timed collection](examples-advanced.html#switch-between-collection-and-ready).
- **`State.onEnter` / `State.onExit`** Add callbacks for entering a state or leaving it through a transition or completion. Use them for actions such as updating a dashboard label. Cancellation of the whole machine can skip its state callback, so put hardware cleanup in the child command’s own exit action. [Show which collection state is active](examples-advanced.html#switch-between-collection-and-ready).
- **`StateMachine.run` / `StateMachine.name` / `StateMachine.requirements` / `ParallelGroup.run` / `ParallelGroup.name` / `ParallelGroup.requirements` / `ParallelGroup.priority` / `SequentialGroup.run` / `SequentialGroup.name` / `SequentialGroup.requirements` / `SequentialGroup.priority`** These types implement the same command lifecycle and inspection methods. Schedule the finished object like any command. Group commands hold their combined requirements. State commands take their requirements as children of the machine. [Compare group and child ownership](ownership.html#move-the-drivetrain-then-position-the-elevator).

## Connect operator controls

- **`CommandGenericHID`** Use `getCommandGenericHID` for the shared wrapper for a scheduler and Driver Station port, or `getHID` to access the underlying device. Bind numbered inputs with `button`. Bind a POV direction with `pov`, or choose `povUp`, `povUpRight`, `povRight`, `povDownRight`, `povDown`, `povDownLeft`, `povLeft`, `povUpLeft`, or `povCenter`. Use `axisLessThan`, `axisGreaterThan`, or `axisMagnitudeGreaterThan` for threshold triggers, and `getRawAxis` for a numeric reading. Use `isConnected` to check the device and `setRumble` for controller feedback. [Bind a numbered button and read an axis](examples-advanced.html#bind-buttons-and-sensors).
- **`CommandJoystick`** Use `trigger` or `top` to bind the named joystick switches. Read `getX`, `getY`, `getZ`, `getTwist`, `getThrottle`, `getMagnitude`, `getDirectionRadians`, and `getDirectionDegrees` for continuous control. Inspect channel assignments with `getXChannel`, `getYChannel`, `getZChannel`, `getTwistChannel`, and `getThrottleChannel`. Set them with `setXChannel`, `setYChannel`, `setZChannel`, `setTwistChannel`, and `setThrottleChannel`. Use `getHID` for the generic command wrapper and `getJoystick` for the underlying joystick. [Use a joystick axis in a default command](changes.html#set-priorities-and-defaults).
- **`InternalButton` / `InternalButton.setPressed` / `InternalButton.setInverted`** Make a software-controlled trigger. Set the pressed state from your code and invert which value counts as pressed if needed. This is useful in a test that wants to drive a binding without a USB controller. [Test a binding with a software button](examples-advanced.html#bind-buttons-and-sensors).
- **`JoystickButton` / `POVButton` / `NetworkButton`** Construct a trigger backed by a numbered HID button, a POV direction, or a NetworkTables boolean. They inherit the `Trigger` bindings. For example, `new JoystickButton(hid, 1).onTrue(announce)` connects a specific device and button number to a command. [See how a trigger binds to a command](examples-advanced.html#bind-buttons-and-sensors).

## Run system identification

- **`SysIdRoutine` / `Config` / `SysIdMechanism`** Build a routine from a test configuration and a mechanism adapter. The configuration holds the voltage ramp, step, timeout, and state logging callback. The adapter supplies a voltage consumer, measurement logging callback, and the Commands v3 mechanism the test requires. [Configure a characterization routine](examples-advanced.html#build-sysid-test-commands).
- **`Config.defaults` / `Config.useDataLog`** Build the standard SysId configuration or supply a ramp rate, step voltage, and timeout while using WPILib’s default data-log state recorder. Use the full constructor to supply your own state recorder. [Compare the configuration options](examples-advanced.html#build-sysid-test-commands).
- **`SysIdRoutine.quasistatic` / `SysIdRoutine.dynamic`** Return commands that require the supplied mechanism. The quasistatic test ramps voltage, and the dynamic test applies a step. Pass `Direction.FORWARD` or `Direction.REVERSE` to select the test direction. [Build all four test commands](examples-advanced.html#build-sysid-test-commands).

## Export scheduler telemetry

- **`CommandProto` / `MechanismProto` / `SchedulerProto`** Protobuf adapters for publishing metadata about a command, mechanism, or scheduler. Use the scheduler adapter exposed as `Scheduler.proto` to encode a scheduler snapshot. [WPILib scheduler telemetry example](https://docs.wpilib.org/en/latest/docs/software/commandbased/commands-v3/telemetry.html).
- **`CommandProto.getTypeClass` / `MechanismProto.getTypeClass` / `SchedulerProto.getTypeClass` / `CommandProto.getDescriptor` / `MechanismProto.getDescriptor` / `SchedulerProto.getDescriptor`** Identify the Java value type and the wire message schema. These support generic logging and publishing code. For example, `Scheduler.proto.getDescriptor()` identifies the snapshot schema. [WPILib scheduler telemetry example](https://docs.wpilib.org/en/latest/docs/software/commandbased/commands-v3/telemetry.html).
- **`CommandProto.createMessage` / `MechanismProto.createMessage` / `SchedulerProto.createMessage` / `CommandProto.pack` / `MechanismProto.pack` / `SchedulerProto.pack`** Allocate a message or fill one with a snapshot. For example, `var message = Scheduler.proto.createMessage(); Scheduler.proto.pack(message, scheduler);` records scheduler state in the message. [WPILib scheduler telemetry example](https://docs.wpilib.org/en/latest/docs/software/commandbased/commands-v3/telemetry.html).
- **`CommandProto.unpack` / `MechanismProto.unpack` / `SchedulerProto.unpack`** These methods are part of the adapter interface and throw `UnsupportedOperationException` in Alpha 8. A telemetry snapshot describes state for inspection and cannot recreate live robot behavior. [Read about scheduler telemetry](https://docs.wpilib.org/en/latest/docs/software/commandbased/commands-v3/telemetry.html).

Coverage is based on the Java API shipped with [WPILib 2027 Alpha 8](https://github.com/wpilibsuite/allwpilib/releases/tag/v2027.0.0-alpha-8). Overloads and related device inputs share entries. The index omits Java-generated record, enum, and object utilities and the generated wire-message classes.
